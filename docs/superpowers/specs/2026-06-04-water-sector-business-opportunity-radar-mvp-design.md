# 水务系统商机雷达 MVP 最小实现设计

## 1. 目标

本次最小实现的目标不是完成完整招投标管理平台，而是先做出一个可运行、可演示、可验证业务价值的 MVP。

第一版只解决 4 个核心问题：

1. 能从 1 个公开来源获取真实招标公告
2. 能根据关键词和基础规则识别相关商机
3. 能在后台查看商机列表和详情
4. 能人工更新跟进状态并记录备注

本版重点是验证“自动发现商机”是否成立，而不是一次性完成报价、附件解析、AI 摘要、竞品分析等完整能力。

## 2. 范围

### 2.1 本期包含

- FastAPI 单体应用
- SQLite 本地数据库
- 1 个采集源接入
- 手动触发采集
- 关键词管理
- 商机评分与等级划分
- 商机列表页
- 商机详情页
- 跟进状态更新
- 跟进备注记录
- 单管理员账号登录

### 2.2 本期不包含

- PDF / Word / Excel 附件解析
- AI 摘要和推荐理由大模型生成
- 企业微信推送
- 复杂权限系统
- 多采集平台统一调度
- 自动定时任务面板
- 竞争对手分析
- 报价系统
- 资料包生成

## 3. 技术方案

### 3.1 技术选型

- 后端框架：FastAPI
- 模板渲染：Jinja2
- ORM：SQLAlchemy
- 数据库：SQLite
- 数据校验：Pydantic
- 前端样式：原生 HTML + 简单 CSS
- 采集方式：requests + BeautifulSoup

### 3.2 选择原因

- 从零开始时，单体应用开发最快
- 服务端渲染可以减少前后端分离的复杂度
- SQLite 方便本地开发和演示
- 规则匹配优先于 AI，更容易验证业务价值

## 4. 系统结构

系统分为 5 个最小模块：

### 4.1 认证模块

- 提供最简单登录页
- 第一版只保留 1 个管理员账号
- 登录后进入商机列表页

### 4.2 采集模块

- 从 1 个公开平台抓取公告列表和详情
- 提供“手动触发采集”入口
- 对公告做去重后入库

### 4.3 规则引擎模块

- 根据关键词命中情况打分
- 根据地区匹配和截止时间补充分数
- 输出商机等级和推荐原因

### 4.4 商机管理模块

- 展示商机列表
- 支持查看详情
- 支持人工修改状态
- 支持添加跟进备注

### 4.5 关键词管理模块

- 新增关键词
- 编辑关键词
- 删除关键词
- 设置关键词分类和权重

## 5. 业务流程

```text
手动触发采集
-> 获取公告列表
-> 抓取公告详情
-> 公告去重
-> 保存原始公告
-> 关键词匹配
-> 计算评分
-> 生成商机记录
-> 后台展示
-> 人工跟进和更新状态
```

## 8. 评分规则

第一版使用固定规则，不引入模型判断。

### 8.1 评分项

- 标题命中 A 类关键词：+35
- 正文命中 A 类关键词：+25
- 正文命中 B 类关键词：+15
- 命中 D 类关键词：+15
- 命中重点地区：+15
- 截止时间未过期：+10

总分上限 100 分。

### 8.2 重点地区

- 深圳
- 广州
- 东莞
- 惠州
- 佛山
- 珠海
- 中山

### 8.3 商机等级

- S：90-100
- A：75-89
- B：60-74
- C：40-59
- D：0-39

### 8.4 推荐原因生成

推荐原因由规则拼接生成，例如：

```text
项目标题命中“不锈钢水箱”，正文命中“安装”，地区为深圳，投标截止时间未过期，因此判定为高价值商机。
```

## 9. 去重策略

第一版采用简单去重：

- 优先使用 `source_url` 去重
- 如果来源链接变化，则使用 `title + publish_date + source` 生成哈希去重

该方案足以支持 MVP，但后续应增加更稳健的正文相似度去重策略。

## 10. 错误处理

### 10.1 采集失败

- 记录失败日志
- 页面提示本次采集失败
- 不影响已有数据展示

### 10.2 页面异常

- 对关键页面返回友好错误提示
- 不在页面暴露堆栈信息

### 10.3 数据缺失

- 预算金额、截止时间等字段允许为空
- 缺失字段不阻塞公告入库
- 评分时按“未命中”处理

## 11. 初始化数据

第一版需要预置以下数据：

- 管理员账号 1 个
- A / B / C / D 类基础关键词一批
- 默认跟进状态集合：
  - 新发现
  - 已查看
  - 已联系
  - 已报名
  - 已报价
  - 已投标
  - 已中标
  - 未中标
  - 不适合

## 13. 验收标准

满足以下条件即可认为 MVP 可用：

1. 本地可以启动系统并登录
2. 可以维护关键词
3. 可以手动触发一次采集
4. 可以抓取到真实公告并入库
5. 可以对公告生成评分和等级
6. 可以在列表页查看商机
7. 可以在详情页查看公告正文和评分原因
8. 可以人工修改跟进状态
9. 可以记录至少一条跟进备注

## 14. 开发顺序

建议按以下顺序实施：

1. 初始化项目结构
2. 建库和模型定义
3. 登录和基础页面框架
4. 关键词管理
5. 采集脚本
6. 匹配和评分逻辑
7. 商机列表与详情
8. 跟进状态与备注
9. 初始化数据和本地演示

## 15. 风险与取舍

### 15.1 最大风险

- 单个平台页面结构变动导致采集失效
- 字段抽取不完整导致评分不稳定
- 第一版 UI 简陋，但这不影响验证业务价值

### 15.2 关键取舍

- 优先“真实数据闭环”，不优先“复杂界面”
- 优先“规则可控”，不优先“AI 自动判断”
- 优先“本地可跑”，不优先“完整生产部署”
